첨부 소비001~004 CSV를 그대로 보존하고 파일명만 `consumer_001.csv`~`004.csv`로 바꿨습니다. 원본명과 SHA-256은 `data/manifest.json`에 있습니다. 다음 숫자는 실제 파일을 파싱한 값입니다.

|입력|사용자 ID|기간|거래 수|열 수|source|
|---|---|---|---:|---:|---|
|consumer_001|USR-DEMO-002|2026-06-06 ~ 2026-09-03|337|32|SEED|
|consumer_002|USR-DEMO-003|2026-06-08 ~ 2026-09-03|193|32|SEED|
|consumer_003|USR-DEMO-004|2026-06-06 ~ 2026-09-03|262|32|SEED|
|consumer_004|USR-DEMO-005|2026-06-06 ~ 2026-09-02|188|32|SEED|

**합계: 980건.** 네 파일은 서로 다른 사용자입니다. 하나의 Twin에 합쳐 학습하지 않습니다. 관측 사이 무거래일은 0으로 포함합니다. 전체 데이터의 관측 시작/종료 밖까지 0으로 늘리지 않습니다.

## 원문만으로 알 수 없는 것

현재 계좌 잔액, 신용/체크 구분, 기발생 카드 미청구·청구 잔액, 실제 카드 출금일, 부채 잔여 원금·금리·원금/이자 구분, 투자 평가액, 보험 보장 범위, 사용자가 승인한 예산·목표, 내부 이체의 미연결 목적지, ATM 인출 후 소비는 제공되지 않았습니다. 이 때문에 CSV-only 모드는 상대 자원 변화량을 보여주고 절대 잔액·목표 확률을 `null`/`insufficient_data`로 반환합니다.

`examples/snapshot_*.json`의 현재 잔액 등은 **USER_ASSUMPTION 데모 가정**입니다. 001=300만원, 002=90만원, 003=500만원, 004=200만원. 003의 투자 1,200만원·대출 1억원도 임의 데모 입력이며 원자료 사실이 아닙니다. 모든 투자·부채를 보고했다고 가정하지 않아 총순자산은 미상입니다.

## 검토가 필요한 의미 차이

- 첨부 요구사항 7봉투·22세분류와 CSV 자체 분류가 다릅니다. `docs/CATEGORY_MAPPING.md`는 그 차이를 드러내는 어댑터 매핑이며, 원문 분류를 몰래 수정하지 않습니다.
- 월세·보험료·통신비 등은 고정 소비로 남으며 현재 7봉투 안에서는 기타로 배정됩니다. 원리금은 별도 `debt_service`입니다. 제품에서 고정비 봉투 차감 정책을 확정해야 합니다.
- `모임 정산` 입금은 소득 모델의 급여로 합치지 않으며 연결할 원거래 ID가 없어 소비 봉투와 임의 상계하지 않습니다.
- 소비003의 동일 지급자 정기 유지보수 수입과 비정기 프로젝트 수입은 `is_recurring`을 구분해 반복 일정의 과대 추정을 방지합니다.
- 소비002 동일 월세 지급자의 같은 날짜 여러 행은 합산한 반복 일정으로 봅니다. 반복 여부는 실거래 확정이 아니라 관측 기반 추정입니다.
- 페르소나 설명의 충동 성향은 원문 설명으로만 유지합니다. 연령/이름/지역으로 신용위험·소비 패턴을 만들어내지 않습니다.

## 금융 API 문서 참조 범위

첨부 `금융_api.zip` 내부 문서 목록과 계좌·카드·대출·정기결제 관련 Markdown을 확인했습니다. API 자격증명/호출은 사용하지 않았습니다. 카드 문서 2.8.12의 청구서 발행과 실제 출금일은 다릅니다. 데모의 `payment_delay_days`는 시뮬레이션 정책 입력이며 금융망 실동작 검증 결과가 아닙니다. API 원본 ZIP은 불필요한 중복 배포를 피하려고 포함하지 않았습니다.
