# 구현 검토 기록

## SPEC 대비 주요 판단

1. CSV에 현재 잔액이 없으므로 '이력 합계=현재 잔액'을 금지했다.
   history-only 결과를 실패로 버리지 않고 상대 자금 여력/소비/일정을 반환한다.
2. 카드라는 단어만 보고 신용/체크를 추정하지 않는다. 종류와 정산 계좌를 snapshot에서 요구한다.
   신용 승인과 청구 출금은 별도 상태 변수이며, free cash를 계산할 때 미결제액을 뺀다.
3. 투자 이체와 ATM 인출은 현금 지출 준비에 영향을 주지만 소비/순자산 손실로 처리하지 않는다.
4. 원리금 납부의 '이자 부분'을 발명하지 않는다. 현금 유출은 반영하되 원금 상태 업데이트는 하지 않는다.
5. 반복 가맹점의 동일일 복수 행을 합산한다. 학생 월세 50만원+관리분 5만원을 55만원 일정으로 처리한다.
   같은 고객사의 정기 유지보수 수입과 큰 비정기 프로젝트 수입은 힌트로 분리한다.
6. 기존 일정 override 시 원거래가 stochastic pool에 되살아나 이중 반영되지 않도록 했다.
7. 같은 random bundle을 공유하여 what-if/optimize에서 표본 잡음이 효과 차이로 보이지 않게 했다.
8. 목표는 미래 잔액 자체가 아니라 미결제 카드·reserve를 차감한 유동 자금으로 정의했다.
9. 이미 안전한 상태에서 불필요한 절약을 권고하지 않도록 최소 변경 목적함수를 사용했다.
10. 동일 날짜라도 거래/취소 이후 기존 snapshot을 dirty로 표시한다. 이 갱신 경계는 날짜 비교만으로 충분하지 않다.
11. 누적값이 안전한 JSON 정수 범위를 벗어나거나 job/후보가 너무 크면 명시적으로 거부한다.
12. snapshot_dirty도 input_digest에 포함하여 같은 잔액 JSON이라도 관측의 유효 상태가 달라진 결과를 구분한다.
13. 시각화에서 null을 0으로 그리지 않으며 확률축을 [0,1]로 제한했다.

## 수행 검토 방식

소스/계약 검토와 자동 테스트를 같은 작성 세션에서 수행했다. 독립 외부 보안감사나 금융 전문가
검토를 받았다는 뜻은 아니다. 단위·계약·통합 테스트와 실제 4개 데이터 실행은 QA_REPORT에 기록했다.

## 남겨둔 운영 검토 항목

- 실사용자/실기관 데이터로 수집 누락, 계좌 범위, 중복 원거래, 카드 할인/납부일을 대사할 것.
- 짧은 이력/한 번의 큰 학비/비정기 수입을 어떤 모델로 처리할지 별도 validation cohort로 선택할 것.
- 합성 데이터에서 보이는 성능을 실제 사용자 성능으로 일반화하지 말 것.
- 공휴일 달력/거래시각별 liquidity/부채 amortization/투자 stochastic model/보험 보장은 확장 작업이다.
- 정책·상품 추천 및 이체 실행은 이 엔진에 넣지 말고 별도의 승인·권한 경계 뒤에 둘 것.
- 인증·암호화·감사 로그 보존정책·bitemporal event history·대규모 다중 사용자 저장소는 운영 호스트에서 설계할 것.
