# 생활 코칭: 숫자 조회에서 다음 행동과 재점검으로

## 무엇을 해결하는가

사람이 앱을 여는 이유는 시뮬레이션 모드를 실행하기 위해서가 아니다. 계좌 잔액과 써도 되는 돈을 혼동하거나, 결제가 몰리는 날을 놓치거나, 이미 예산을 넘겨 이후 행동을 정하지 못할 때 판단을 돕기 위해 연다.

제품의 기본 흐름은 **상황 확인 → 지금 필요한 행동 하나 → 사용자가 선택 → 새 거래로 재점검**이다. 모든 방문에서 감축을 권하지 않는다. 변경할 이유가 없으면 현재 계획을 유지하도록 하고, 자료가 부족하면 필요한 사실부터 확인한다.

| 실제 사용 시점 | 필요한 도움 | 성공 조건 |
|---|---|---|
| 평소에 앱을 열었을 때 | 다음 결제, 계좌별 여유, 실제 예산 사용을 한 번에 확인 | 사용자가 계산 모드를 고르지 않아도 우선할 행동이 보인다. |
| 구매하거나 큰 지출을 앞뒀을 때 | 금액·날짜·결제수단을 반영한 변경 전후 비교 | 소비 감소, 통장 잔액, 카드 미결제액, 따로 보관한 돈을 혼동하지 않는다. |
| 받기로 한 돈이 늦어질 때 | 어느 결제 계좌가 먼저 어려워지는지 확인 | 해당 입금 한 건의 날짜만 바뀌며 소득 감소로 둔갑하지 않는다. |
| 돈을 따로 남겨둘 때 | 보관하면서 나머지 생활이 가능한지 확인 | 보관은 소비가 아니고, 예정 지출일까지 보관하면 실제 지급 시 중복 차감되지 않는다. |
| 예산이 빠르게 줄거나 계획을 넘겼을 때 | 지킬 수 있는 기간별 추가 지출 한도를 직접 비교·선택 | 임의 감축률이나 필수 생활비 절감을 정답처럼 제시하지 않는다. |
| 다음 주 또는 새 거래를 연결했을 때 | 내가 정한 한도와 관측된 지출을 비교 | 자료가 부족하면 성공 판정을 보류하고, 초과했으면 다음 계획을 재설정한다. |

이 목록은 고정된 시연 질문 목록이 아니다. 입력 자료와 실제로 달라지는 일이 있을 때 동작하는 제품 흐름이다. 검증도 문장 열 개에 대한 숫자가 아니라 회계·날짜·결정·후속 관찰의 의미를 검사한다.

## 화면과 계층

- `/`: 생활 코칭 홈. 모드·경로 수·난수 시드는 기본 UI에서 제거했다.
- `/workbench`: 기존 자료 연결/갱신 화면과 전문 분석 도구. 기존 수치 API와 5개 모드는 호환성을 위해 유지한다.
- `fdt/coaching_contract.py`: 날짜, 보호할 현금, 실제 변경 행동의 명시적 입력 계약.
- `fdt/coaching_projection.py`: 기존 `generate_bundle` / `simulate`를 사용하되 지출·카드 미결제·보관액을 별도 장부로 계산한다. 다섯 모드로 질문을 우회하지 않는다.
- `fdt/coaching.py`: 관측, 변경 비교, 우선 행동, 다음 점검 근거를 만든다.
- `workbench/coaching.py`: 코칭 API와 명시적으로 저장한 사용자 계획. 계획은 별도 SQLite이며 관측 Twin을 바꾸지 않는다.
- `_numeric_app.py`, `_numeric_jobs.py`: 기존 구현을 그대로 보존한다. 새 `app.py`, `jobs.py`가 생활 코칭과 기존 분석에 동일한 로컬 보안·단일 작업·취소·타임아웃을 적용한다.

## 입력과 행동

`POST /api/twins/{record_id}/coaching`에 `through_date`를 전달하면 별도 모드 선택 없이 전체 점검을 한다. 서버의 `Asia/Seoul` 날짜가 기본 `on_date`다. 다른 날짜를 검토하려면 `replay: true`를 명시해야 한다.

```json
{
  "on_date": "2026-09-08",
  "through_date": "2026-09-15",
  "protected_cash_krw": 200000,
  "changes": [
    {
      "kind": "expense",
      "label": "미리 준비할 비용",
      "date": "2026-09-13",
      "account_id": "실제 계좌 식별자",
      "amount_krw": 200000,
      "reserve_now": true
    }
  ]
}
```

이 예시는 API 계약 설명이다. 금액·날짜·계좌를 자연어에서 자동 추측하지 않는다. `GET /api/twins/{record_id}/coaching/context`에서 해당 자료의 계좌·카드·입금 일정을 선택한다.

지원 행동은 다음과 같다.

- `expense`: 구매/지출일, 금액, 계좌 또는 카드. 신용카드는 실제 출금일을 추가로 요구한다. `reserve_now`는 계좌 지출을 지급일까지 보관하는 선택이다. 예산 항목 미지정 지출은 현금에 반영하되 임의로 봉투에 배분하지 않는다.
- `set_aside`: 계좌의 일정 금액을 추가 소비에서 제외한다. 통장 잔액과 소비액은 변하지 않으며 실제 이체가 아니다.
- `income_delay`: `rule_id`와 `original_date`로 한 건을 지정해 `new_date`로 옮긴다. 같은 경로의 같은 입금액을 유지한다. 기간 밖으로 옮기면 미수령 기간임을 표시한다.
- `spending_cap`: 승인된 예산 항목의 미래 시작일~종료일에 추가로 쓸 총 한도. 확정/추정 정기 지출을 취소하지 않고 변동 지출을 한도 내로 제한한 가정을 비교한다. 예정 지출 자체가 한도를 넘는 경로는 별도로 표시한다. 동일 항목에 중복 한도를 받지 않는다.

`protected_cash_krw`는 요청값 또는 스냅샷 값의 출처를 표시한다. 둘 다 없으면 0원으로 조용히 채워서 추가 소비를 권하지 않는다. 계산 자원 기본값은 400경로·seed 42이며 결과에 출처를 남긴다.

## 결론을 과장하지 않는 규칙

관측 기준일과 질문 날짜가 다르면 오늘의 가용금액 산출을 보류한다. 최근 거래와 같은 날짜의 잔액·카드 청구가 필요하다. 과거 재생을 오늘의 코칭으로 보여주지 않는다.

기간 중 한 번이라도 부족한 경로와 마지막 날 부족한 경로를 별도로 반환한다. 0/400은 관측된 모델 경로에서 0회라는 의미이며 현실 확률 0%가 아니다. P10은 최악의 경우나 보장 하한이 아니다.

예산 잔여는 각 경로에서 `승인 예산 - 관측 사용 - 해당 기간 예상 사용`을 구한 다음 분위수를 계산한다. 다음 달 예산은 자동 반복 승인하지 않는다. 통장 여유는 계좌별·기간별 최소 현금과 카드 미결제액·보관액·보호할 현금을 함께 고려한다. 계좌별 여유는 더해서 쓸 수 없다.

현금 설명은 소득, 정산 유입, 직접 소비, 고정지출, 카드 실제 정산, 채무 상환, 저축 이동, 현금 인출을 **경로 평균**으로 연결한다. 중앙값 항목을 더해서 중앙값 잔액을 설명하지 않는다. 내부 계좌 이동은 전체 현금에서 상계된다. 카드 정산액은 현금/미결제 전이의 정합식으로 계산하며 구매액을 두 번 지출 처리하지 않는다.

새 신용카드 구매는 사용자가 지정한 실제 출금일까지 점검하지 않았다면 결제 준비 판단을 보류한다. 기존 생활 소비의 카드 정산은 기존 엔진의 단순화된 일정 모델을 계속 사용한다. 실제 약관·영업일·당일 순서는 모델 밖이므로 확정 청구와 잔액을 확인해야 한다.

생활 코칭 범위는 1~90일이다. 이는 정확도를 보장하는 통계적 경계가 아니라 가까운 행동과 재점검에 집중하기 위한 제품 범위다. 이력보다 긴 점검이나 짧은 관측 이력에는 추가 주의를 표시한다. 더 긴 기간은 기존 전문 분석 도구에서 조건부 시나리오로 볼 수 있다.

## 계획 저장과 후속 점검

`POST /api/twins/{record_id}/coaching/plans`는 `label`, `action`, `confirmed: true`를 요구한다. 현재 추적 지원은 미래 기간의 `spending_cap`이다. 과거 자료 재생 UI에서는 실제 계획 저장을 제공하지 않는다.

계획은 화면의 일회성 레코드 ID가 아니라 안정적인 `twin_id`로 연결한다. 같은 사용자의 새 자료를 생성해도 계획을 이어서 볼 수 있다. 사용자별 최대 30개이며 직접 삭제할 수 있다. 리뷰 호출은 저장된 계획을 시뮬레이션에 자동 반영하지 않는다. 사용자가 지키기로 했다는 이유로 이미 지켰다고 가정하면 안 된다.

후속 점검은 시작일부터 관측 종료일까지 예산에 포함된 실제 지출을 집계한다. 월초/계획 시작 이력이 없거나 미분류 지출이 있으면 완료 판정을 보류한다. `within_cap`은 해당 자료의 한도 내 사용이지 코칭의 인과적 절약 효과가 아니다. 돈을 이체하거나 알림을 예약하는 기능은 없다.

## 현재 범위 밖

자유 문장의 자동 의미 해석, 은행 연결/실제 이체, 실세계 확률 보정, 하위분류별 행동 예측, 교통수단 변경의 인과 효과, 자동 예산 재배분, 장기 목표 최적화는 구현했다고 주장하지 않는다. 하위분류가 없는 자료를 임의의 외식 비율로 바꾸거나, 늦은 입금을 소득 감소로 바꿔 답하지 않는다. 필요한 사실은 명시적 입력이나 자료 갱신으로 받는다.

## 회귀 검증

`tests/test_coaching.py`는 기간 위험과 만기 위험, 오래된 자료, 예비금 출처, 카드 출금 시점, 당일 구매, 보관/지급 중복 차감, 한 건의 입금 지연, 시작일이 있는 한도, 예정 지출 보호, 잔여 분위수, 월 경계, 현금 정합식, 후속 관측, 미지원 입력을 검사한다. 기존 4개 페르소나도 실제 엔진으로 점검한다.

`tests_web/test_coaching_api.py`는 기본 홈, 기존 분석 호환, 기준일, 실제 spawn 작업, 세션 토큰, 명시적 계획 저장, 사용자 격리, 자료 재생성 뒤 계획 유지와 SQLite 지속성을 검사한다. GitHub Actions에서 기존 수치/웹 테스트와 함께 실행한다.
